# 1.1.0 implementation plan

Written 10 November 2026 after replicating every card on the lab (`docs/qa/replication-1.1.0.md`) and reading the
code each fix touches. Order is by what a customer feels. Every item lists the cause, the change, which entry points
it reaches (wizard, REST, WP-CLI) and the check that must fail on 1.0.0 and pass after.

Rules that shape every item: product APIs only, everything recorded in the ledger, never touch the owner's users or
content, exact plan counts, no new table or option without the owner's yes.

## Batch F: AI site builder (WordPress core AI connectors only)

Two modes, one wizard (owner, 11 November 2026): AI is a selling point, but most owners will not use it, so the
non-AI path stays exactly as in 1.0 and comes first. The AI entry is one optional bar on the Starting point step
("Have a site in mind?"); without a connector only administrators see one quiet tip line there. The site check never
shows AI.

Owner decisions, 10-11 November 2026: AI runs only through the connectors WordPress core provides (Settings >
Connectors: Anthropic, Google, OpenAI, each with the owner's own key; core passes the key to its AI client). The
installer ships no AI service, key setting or adapter. Lab WordPress 7.1.3: `wp_get_connectors()` lists anthropic,
google, openai; with no key `wp_ai_client_prompt()->is_supported_for_text_generation()` is false.

| Choice | Decision |
|---|---|
| How AI helps | The owner writes one sentence; the AI proposes **3 ready site ideas**; the owner picks one and the wizard fills itself in |
| How far it goes | Setup (starting point, products, name, tagline) **plus text written for the niche**, in the site's language. Photos come from our CC0 library, chosen by meaning. No AI images |
| No connector set up | A short card on the site check: connect Anthropic, Google or OpenAI in Settings > Connectors, with a link. Everything else works as now |
| Testing | The owner adds a real key in the lab's Settings > Connectors (never shared); a lab-only mock provider gives repeatable checks |

Flow:

1. **Seam** `src/Ai/Assistant.php`: `available()` is `function_exists( 'wp_ai_client_prompt' ) && wp_supports_ai()` and
   `is_supported_for_text_generation()`; `json( $system, $prompt, $schema )` runs `wp_ai_client_prompt()` with
   `using_system_instruction()`, `as_json_response( $schema )` and a request timeout, decodes, and returns array or
   WP_Error. Nothing else calls the AI. Site check gets `ai` (available, connector names, link to
   `options-connectors.php`).
2. **Ideas**: REST `POST /ideas` with the description. The prompt carries the site language (`get_locale()`), the
   starting points, the supported products with one line each (installed or installable from the catalog), and what
   each builds. Schema: 3 ideas, each name, tagline, starting point (enum), products (enum), why each product fits,
   highlights (spaces, courses, events the site will have), tone and niche words. Validated server side: unknown ids
   dropped, lengths capped, text sanitised. Wizard step 1 shows the 3 cards; picking one ticks missing free products
   in the install panel, sets starting point, products, name and tagline, and keeps the idea as the **brief**.
3. **Review** shows what the AI will write and that each product's text is written by the owner's AI connector
   (requests billed to their account), with exact counts as today.
4. **Content packs**: `start_build` stores the brief; the queue starts with one `__ai` step per included provider
   (split by content key for the big files: Jetonomy, BuddyNext, WPMediaVerse, people bios) before any content step.
   Each step sends the provider's curated content and its **text paths** (each provider declares `ai_fields()`, for
   example `spaces.*.name`, `spaces.*.desc`, `companies.*.1`) and returns the same structure. Validation: identical
   shape, array lengths and every non-text value (slugs used as references, indexes, roster numbers, enum values,
   prices, dates); text values strings within length caps; `{@N}` mention tokens kept; image fields only from the
   photo manifest. A pack that fails is dropped with a warning ("WB Listora: the AI text did not pass the check, so the
   sample text was used"); the build never fails because of AI. Valid packs go into state refs and reach providers
   through the existing `wbcom_demo_content` filter.
5. **Photos by meaning**: `media/manifest.php` lists the 43 photos with subject tags (from file names and
   CREDITS.json titles); image fields in a pack may only name a manifest photo of the same kind (space covers stay
   landscape, avatars never change: they are the sample people's faces).
6. **Order fixes this needs**: BuddyNext decides which hashtags are new at its first content step (not in `steps()`),
   after the packs exist. Visible slugs follow the new names where the product takes a slug (internal reference keys
   stay).
7. **Same engine**: everything is recorded and removable; plan counts are unchanged because the shape is fixed.
8. **WP-CLI**: `wp wbcom-demo ideas "<description>"` prints the 3 ideas; `build --describe="<description>" [--idea=<n>]`
   builds from one (first by default).

Safety: AI output is untrusted text; it goes through the same product APIs and sanitising as curated content, no
HTML beyond what the product allows, no links, no new option names. The description, the site language and the
product list are sent to the owner's chosen provider, and the wizard says so next to the box.

Checks: ideas and packs against the real model (owner's key) and the mock; a pack that breaks shape, drops a mention
token or names an unknown photo is rejected and the curated text is used; Remove everything leaves nothing; non-English
site language; no connector shows the card and every other path works.

## Risks found while planning

1. **Pro toggles load at boot.** Learnomy Pro and Listora Pro read their feature list when they boot, so a toggle set
   in a step only takes effect on the next request. The wizard runs one step per request, so it works there; WP-CLI
   runs all steps in one process, so Pro content steps would see the feature off. Plan: CLI runs each step in its own
   process (`WP_CLI::runcommand( 'wbcom-demo step', array( 'launch' => true ) )`), which also fixes the 128 MB
   problem for long builds and matches the wizard exactly.
2. **Pro extensions need a licence** (Jetonomy Pro): a demo on a site without a licence shows Pro as "needs licence".
3. **Product gaps** that need cards on the product boards (we work around them, never edit products): WPMediaVerse
   challenge delete; BuddyNext subscription delete; Jetonomy `Post::create` not firing its create action.
